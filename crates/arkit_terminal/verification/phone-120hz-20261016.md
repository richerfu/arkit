# Terminal rendering on ALN-AL00 — 2026-10-16

The production rio-vt/wgpu terminal sustains nominal 120 Hz buffer submissions
in two consecutive phone runs. This validates renderer output; local PTY startup
is blocked by the phone sandbox at `allocate PTY: Permission denied (errno 13)`.
The shell never starts, so these measurements do not establish PTY-to-display
throughput or input latency.

Device: ALN-AL00, HarmonyOS `7.0.0.109(SP6C00E105R4P3)`, 1260×2720, scale 3.25.
Build: optimized Rust Release, signed Release HAP, `com.arkit.example`.
The terminal viewport during the workloads is 34×13 cells; the normal page is
34×14 when its shorter status fits on one line.

## Results

Each probe runs ASCII scrolling, CJK/combining-mark/emoji scrolling and styled
viewport rewrites for eight seconds each. A Tokio producer feeds VT every 2 ms
through the production `TerminalInbox`. It does not create a PTY or drive draws.
OHOS NativeVSync drives the terminal worker through
`OH_NativeVSync_RequestFrameWithMultiCallback`.

The table counts RenderService `FlushBuffer` events for the terminal's own
Surface queue, resolved from the app's RS tree. Stable windows cover seconds
2–7.5, 10–15.5 and 18–23.5 relative to the first continuous submission burst.
These windows omit startup and phase-transition warmup.

| Workload | Run 1 FPS | Run 2 FPS | Run 1 P95 interval | Run 2 P95 interval |
| --- | ---: | ---: | ---: | ---: |
| ASCII scroll | 120.773 | 120.774 | 9.599 ms | 9.637 ms |
| CJK/emoji scroll | 120.732 | 120.772 | 9.592 ms | 9.645 ms |
| Styled redraw | 120.778 | 120.793 | 9.564 ms | 9.719 ms |

No interval exceeds 12.5 ms within those six stable windows. Their largest
interval is 11.125 ms. Screen-mode samples at 4, 12 and 20 seconds report 120 Hz
in both runs.

Across the wider 2–23.5 second interval, including phase changes, submissions
average 120.581 and 120.622 FPS. Maximum intervals are 30.940 and 20.090 ms,
with four and three intervals over 12.5 ms respectively. These results therefore
do not establish zero presentation stalls. Buffer submission and active screen
mode are measured; GPU completion and physical panel scanout timing are not.

## Fixes validated on the phone

- Replace the Surface-ID argument passed to `Create_ForAssociatedWindow` with
  an independent `OH_NativeVSync_Create` connection. The associated-window API
  requires a WindowManager window ID, which differs from a NativeWindow Surface ID.
- Request the next callback before GPU acquisition/presentation.
- Reconfigure the existing wgpu/EGL surface when the same NativeWindow resizes.
  Previously, creating a second EGLSurface during layout changes produced
  `eglCreateWindowSurface error` and a wgpu `Invalid surface` panic, terminating
  the render worker. A replacement NativeWindow releases the old surface first.

Both completed workloads visibly update all three phases. The second run starts
after the real PTY permission error changes status/layout. Showing the keyboard,
collapsing it with the input-method arrow, then printing the color sample also
works. Leaving and re-entering the terminal rebuilds its surface successfully.
No further EGL/`Invalid surface` panic was logged for these checks.
